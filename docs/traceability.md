## P1-04 prototype evidence

Scope: the P1-04 task branch on macOS arm64, Rust 1.99.1, SQLx 0.9.0, bundled SQLite 3.51.3. Every journal, ledger, database, and secret store in the fixtures is synthetic and lives in a throwaway `TempDir`; the secret store is a fake in-memory map, so no native store, keychain, application-data directory, production, business, or personal database was opened, read, or written. Commands, per-criterion evidence, and remaining gaps are recorded in [the task validation record](../.trellis/tasks/archive/2026-10/10-18-p1-04-recovery-fences/validation.md).

- A18: injected interruptions before the journal write, after candidate activation, and during cleanup either converge idempotently or stay visibly pending: a durability failure before the first journal write leaves no secret, projection, or lifecycle change; a locked secret store compensates the orphan candidate and never acknowledges; a failed post-commit cleanup leaves `compensation_pending` and recovery repeats the same pending report until the store unlocks. Recovery runs before any mutation or scheduling, removes an orphan candidate the projection never recorded, and one locked connection does not stop recovery for the others. Unparsable or truncated journal and ledger content refuses to open a coordinator, so absent readable state is never read as finished cleanup. A rotation whose candidate is the reference the connection already holds is refused before any journal, projection, or secret write, so compensation can never remove a secret still in use, and a reused operation identifier for a different connection is refused before it can make the journal undecodable. Session-only restart semantics, real provider identity verification, and the credential UI remain pending.
- A20: the deletion ledger is durable before the lifecycle transition, fences dispatch and result writes, and rejects a restore manifest carrying a deleted opaque identifier even after a simulated restore of an earlier database backup whose projection no longer knows the deletion. A failed cleanup does not acknowledge the deletion: the entry stays `pending_cleanup`, scheduling and every restore stay blocked, and the operation is retryable across a restart. A deletion interrupted after its `deletion_pending` transition and before its journal record does not dead-end either: the caller may begin the deletion again, and recovery resumes it from the ledger entry alone, removing the reference the database names and then acknowledging the cleanup. A deletion whose transition was refused, or never committed, is not owed: the ledger is written first, so recovery leaves the row's credential and the `pending_cleanup` entry untouched and the deletion stays retryable. Managed backup creation, purge, and restore execution, retention purges, the local fact purge during deletion, and release deletion certification remain pending.
- A21: journal and ledger files carry opaque identifiers and nonsecret state only; a fixture asserts that no credential value, provider identity, alias, provider account key, or usage metric appears in either file. Failure to establish durability stops the mutation before any secret write. Native secret stores, session-only memory guarantees, and restricted IPC authorization remain pending in P1-05 and P1-07.
- A23: an obsolete generation cannot commit: the final generation, lifecycle, and fence check runs inside the `BEGIN IMMEDIATE` write transaction, and a stale context rolls back with the candidate reference compensated. `set_lifecycle` re-checks the same incomplete-projection fence inside its own write transaction, and scheduling admission consults database projections as well as the external journals, so an operation whose journal record was released but whose projection could not be completed still fences a lifecycle mutation, a dispatch, and a result write. Statistics throughput benchmarks, async desktop integration, and native disk-full behavior remain pending.

## P1-11 prototype evidence

Scope: the P1-11 task branch on macOS 27.0.1 arm64, Rust 1.99.1, Node 24, Tauri 2.12.4 with `tauri-plugin-single-instance` 2.5.4 and `tauri-plugin-notification` 2.7.0. Automated checks use synthetic providers, fake or session-only secret stores, and throwaway `TempDir` roots; the renderer checks run in jsdom, not a native WebView. The native smoke runs used a throwaway `$TMPDIR/quotavista-prototype` data directory and `QUOTAVISTA_SECRET_STORE=session-only`, so no real keychain entry, application data directory, provider endpoint, or production database was read or written. Commands, observed native output, and the interactive steps that remain pending are recorded in [the task validation record](../.trellis/tasks/archive/2026-10/10-18-p1-11-desktop-lifecycle/validation.md).

- A11: tray availability is a detection, never an assumption. A successful `TrayIconBuilder::build` counts as available on macOS, where the menu bar is an operating-system shell surface, but not on Linux, where `tray-icon`'s default `libappindicator` backend registers successfully even with no indicator host running; the prototype therefore reports Linux as unavailable until a host probe is validated by a native run. A native macOS launch printed `capabilities tray=Available notification=Unconfirmed` and `QUOTAVISTA_TRAY=off` printed `capabilities tray=Unavailable notification=Unconfirmed` — the notification channel reads unconfirmed because the pinned plugin cannot read the operating system's answer, and reporting it as available would have been a promise nobody kept. Single instance was observed natively: a second launch exited immediately with status 0 while the first instance kept running and logged the handover. The close/reopen/quit policy itself is unit-tested (`closing_the_main_window_exits_when_no_tray_was_detected`), but driving a real window through the tray menu, the notification banner, and every Ubuntu 26.04 GNOME check remain pending a human native run through `scripts/native-checks.sh --interactive`.
- A07: wake merges permitted refresh work instead of replaying missed timers. Two independent sources feed it: the reactivation signals a window server emits (`WindowFocused`, macOS-only `ReopenWithoutVisibleWindow`, `SingleInstanceActivation`) and `ResumeMonitor`, which compares the monotonic and wall clocks on the composition runtime and therefore detects a suspend gap even while the main window stays hidden in the tray and no window event fires at all. Every source runs through the same gated path, so refresh-Off gating and deduplication hold for all of them. With `refresh_minutes: None`, the shipped default, `handle_wake` returns before the coordinator is touched, so no job is created and no provider can be contacted; a native macOS run confirmed that Off gate on a real handover with `wake SingleInstanceActivation mode Off permitted false merged 0 not-due 0` — evidence of Off gating, not of a sleep cycle. With an interval configured, one wake admits one merged refresh and a second wake inside the interval adds nothing, and a reactivation burst is collapsed by a monotonic gate. Lifecycle work is spawned onto the composition runtime and never `block_on` from the event-loop thread, so a slow refresh cannot freeze window interaction or the user's Quit action; Quit raises a shutdown signal that the wake's pump loop honours between steps. Quit cancels every in-flight job to a terminal outcome without driving a pump, so committed values survive a restart while an abandoned history candidate leaves the published partition untouched. A real machine suspend/resume cycle and the Linux session type remain pending a human native run (`scripts/native-checks.sh --interactive`, steps 14–16).
- A21: a corrupt lifecycle journal aborts the composition before the refresh coordinator is opened, so recovery-before-scheduling ordering is enforced at desktop startup rather than only inside the recovery coordinator. The two new commands carry no credential input and stay behind the existing single-command capability allowlist; no plugin permission was added. Native Keychain and Secret Service behaviour is unchanged from P1-05 and still pending its own evidence.
- A25: the synthetic notification renders from one `template_key` in the active locale, is bounded and free of account identity or credential text, and is deliberately separate from future persistent alert episodes. Delivery is reported in three honest states rather than one boolean: `NotificationPreviewDto.delivery` is `Delivered` only when the platform confirmed it, `Queued` when the adapter handed the notice over without ever reading the result, and `Refused` when the channel could not take it. `NotificationCapabilityDto::Available` is reserved for a confirmed channel, so the pinned desktop plugin — whose `permission_state()` always answers granted and whose `show()` spawns the delivery and discards the operating-system response — yields `Unconfirmed`, which is exactly what the native macOS launch printed. The localized text is returned in every case, so an unavailable or unconfirmed channel still leaves an in-app explanation instead of a silent failure, and both catalogs name the states (`desktop.notification.unconfirmed`, `desktop.notification.queued`). en/zh-CN catalog parity is enforced across all 122 keys each — the 103 P1-09 merged into `main` plus the 19 `desktop.*` keys this task added. Runtime notification delivery in both locales remains pending a native run.
