# P1-07 validation record

## Scope and prerequisites

Backend composition and frontend wiring. P1-07 wires the existing P1-03 storage, P1-04 lifecycle coordinator, P1-05 secret stores, and P1-06 refresh coordinator into the Tauri desktop entry point. It adds a single `dispatch_command` IPC entry that accepts a raw `serde_json::Value`, decodes + validates every request through the contract envelope (`contract_version`, `request_id`, `Command`), maps it into the existing application use cases, and returns a `CommandResult` wrapped in an `Envelope`. The renderer talks to the backend through a narrow generated-type client at `apps/desktop/src/ipc.ts` and subscribes to revision-only `ChangeEvent` notifications. The Tauri capability allowlist on the `main` window permits the `dispatch_command` command plus the two event permissions the revision channel needs (`core:event:allow-listen`, `core:event:allow-unlisten`); every other command-level operation, validation, and safe-error mapping lives behind it.

Prerequisite confirmed before starting: P1-05 is merged (PR #7, merge commit `dc0d14b`) and archived at `.trellis/tasks/archive/2026-10/10-18-p1-05-secret-stores` by archive commit `c076f68`. P1-06 is merged (PR #6, merge commit `4e024c8`) and archived at `.trellis/tasks/archive/2026-10/10-18-p1-06-simulation` by archive commit `62c348d`. P1-04 is archived at `.trellis/tasks/archive/2026-10/10-18-p1-04-recovery-fences` (archive commit `a38d2b4`), and the P1-08 bilingual frontend shell is archived at `.trellis/tasks/archive/2026-10/10-18-p1-08-bilingual-shell`. Branch head on top of main: `main` head `62c348d`.

Every fixture is synthetic and throwaway: `build` opens `SqliteRepository` against a caller-supplied root directory and a `FileStore` rooted at `<root>/journal`, both under a `tempfile::TempDir` in the tests. The desktop integration tests build with `SecretChoice::SessionOnly` (the in-memory fake) and never touch a real keychain, Secret Service bus, application data directory, production database, or business database. Activation was recorded with `python3 .trellis/scripts/task.py start .trellis/tasks/10-18-p1-07-ipc`.

Environment: macOS 27.0.1 arm64, Rust 1.99.1, Node 24.22.0, npm 11.19.1, Tauri 2.12.4, ts-rs emits the generated IPC types into `apps/desktop/src/generated/contracts.ts`.

## Round-2 review response

Review round 2 at `~/.quotavista-orchestration/p1-07-fix-round2.md` (head `2fb5893`) raised four blocking items and two should-fix items. This section records what the branch actually does now, with the test that proves it.

1. **Tauri command argument alignment (blocker 1).** `dispatch_command` takes `request: Option<serde_json::Value>`. The Rust parameter is named `request`, so Tauri's camelCase key is `request`, which is exactly what the renderer sends (`invoke("dispatch_command", { request })`). The argument is optional so a missing key never reaches Tauri's `CommandArg` machinery: the application answers with a sealed `Envelope::Error` (`ErrorCode::Validation`, `request_id: "qv-malformed"`) instead of a framework error. A malformed value is decoded inside the application and produces the same sealed error, and the offending value is never echoed. Proof: `the_generated_handler_accepts_the_renderer_argument_shape` drives the real generated handler through the `tauri::test` mock runtime with the renderer body `{"request":{...}}` and asserts `status: "ok"`; `the_generated_handler_answers_a_missing_argument_with_an_error_envelope` sends `{}` and asserts `status: "error"` with `code: "validation"`; `malformed_request_answers_with_a_sealed_error` and `missing_request_answers_with_a_sealed_error` cover the same two paths through the shared dispatcher.
2. **Refresh admission is executable and pollable (blocker 2).** `refresh_connections` rejects an unknown id in `RefreshTarget::Selected` up front with a sealed `Validation` error, before any job is admitted and without an event. It then submits one `RefreshCoordinator::request_manual` batch and drives `RefreshCoordinator::pump()` (bounded by `MAX_REFRESH_STEPS = 64`) until the admitted jobs are terminal. A job that outlives that step budget is not stranded: `get_operation` advances the coordinator when the polled job has no outcome yet, so polling is the continuation path for a job the refresh command could not finish. The `OperationDto.operation_id` is the coordinator's job id, never the connection id. `get_operation` reads the coordinator's outcome first, then the admission records, and only then the durable lifecycle ledger; an unknown id is rejected with `Validation`. Outcome mapping: `Published`/`Skipped` → `Succeeded`, `Incomplete` → `Failed` with `InvalidResponse` (a partial history never reports sync success), `Cancelled` → `Cancelled`, `Fenced` → `Failed` with `Conflict`, `Cooldown` → `Pending` with `RateLimited` and `retry_at`, a provider error → `Failed` with the typed provider code, a storage error → `Failed` with `StorageError`, and a job that is still running stays `Running`. Proof: `refresh_drives_the_coordinator_and_returns_pollable_job_ids`, `every_returned_operation_id_can_be_polled`, `refresh_rejects_an_unknown_selected_connection`, `a_failed_refresh_publishes_no_change_event`, `a_refused_connection_reports_a_failure_without_an_event`, `get_operation_rejects_missing_id`, `polling_finishes_a_job_that_outlived_the_refresh_budget` (24 seeded connections overrun the refresh step budget, and polling the running job drives the coordinator until the job succeeds).
3. **Commit-only monotonic revision events (blocker 3).** The revision is the store's own commit counter, not the settings revision: `crates/core/src/storage.rs` gained `Repository::data_revision()`, and `crates/infrastructure/src/sqlite.rs` implements it as `SELECT data_revision FROM store_state WHERE id=1`. Every committed snapshot or published partition advances that counter. The desktop emits a `ChangeEvent` only when the counter advanced across the request, so a refresh that failed or wrote nothing announces no change; the event's `data_revision` is the new store revision and the affected ids are the connections whose job completed. `list_connections` reports the same store revision. On the renderer side the tracker keeps two watermarks, and neither ever moves backward: `rendered` is the newest revision the renderer has shown (from a response or from an event) and `announced` is the newest revision received on the event stream. `apply` drops an event that repeats the event stream, lowers neither watermark, and reports an event that is older than the rendered revision as `stale` to the subscribers that have not seen it, so a response observed by one screen cannot silence the invalidation another screen is waiting for. `observe(revision)` refuses a revision that is not newer than the rendered watermark, and `isRevisionGap` reports a skipped revision (`incoming - seen > 1`), so a repeated revision is not a gap. `OverviewScreen` installs the listener before its first read (a commit that lands between the read and the registration would otherwise be missed), reloads on an `apply` and on a `gap` (a skipped revision cannot be patched), disposes the listener when it unmounts, keeps the last known state when the change channel cannot be installed, and discards a response whose `data_revision` is older than the observed revision. `subscribeToChanges` removes the tracker subscription again when the native listener installation fails, so a failed subscription leaves nothing behind. Proof: `change_event_revisions_only_move_forward` (two refreshes, the second revision is strictly greater), `a_failed_refresh_publishes_no_change_event` and `a_refused_connection_reports_a_failure_without_an_event` (no event without a commit), `apps/desktop/src/ipc.test.ts` (12 tests, including that neither watermark is ever lowered, that a rendered response does not silence another consumer's event, that a repeated event does not notify, and that a failed listener installation leaves no subscriber), and `apps/desktop/src/screens/OverviewScreen.test.tsx` (6 screen tests: the listener is installed before the first read, reload on a new revision, reload on a skipped revision, obsolete response discarded, listener disposed, last known state kept when the change channel cannot be installed).
4. **No invented read results (blocker 4).** `get_overview` and `query_statistics` return `SafeError::new(ErrorCode::UnsupportedInPhaseOne, None)`; the stub summary that reported a Jan-1970 interval, revision 0, and empty results is gone. The statistics and overview read ports do not exist in `quotavista-core` yet — the query engine is P1-09's deliverable — so a typed deferred state is the honest answer, and the same is true for the six deferred mutation and settings commands. The deferral is a recorded scope boundary of this task and not a silent gap: the task PRD asks P1-07 for explicit safe states for later-phase actions, and it names P1-09 as the owner of the overview and statistics reads. Proof: `later_phase_commands_return_typed_unsupported_state` asserts `UnsupportedInPhaseOne` for all eight deferred commands.
5. **No silent secret downgrade (should-fix 1).** `SecretChoice` is explicit: `Native` (the platform store) or `SessionOnly` (the in-memory store). `build` takes the choice and never substitutes one for the other. A native store that cannot be opened leaves the composition explicitly degraded: `secrets` is `None`, `degraded` carries the typed error of the actual failure, and no lifecycle coordinator is built. The failure keeps its kind: `SecretError::Locked` becomes `SecretStoreLocked`, `SecretError::Unavailable` becomes `SecretStoreUnavailable`, `SecretError::NeedsCredentials` becomes `NeedsCredentials`, and `SecretError::Validation` becomes `Validation`, because a locked store and a missing backend are different user-actionable states. The degraded composition drops no fence: the refresh path keeps the coordinator's own generation and lifecycle fence, and the refresh coordinator recovers its own counter and cooldowns when it opens. P1-07 writes no journal or lifecycle-ledger entry, because the only commands that write them are the deferred mutation commands, so the lifecycle coordinator's startup reconciliation has nothing to reconcile in this phase. The two secret-dependent commands (`connect_provider`, `replace_credentials`) report that typed degraded error instead of a generic "not implemented". The session store is reachable only through a deliberate choice — `SecretChoice::SessionOnly` in code, or `QUOTAVISTA_SECRET_STORE=session-only` in a production run — and never automatically. Proof: `a_degraded_composition_reports_the_credential_store_error`, `secret_errors_keep_locked_and_unavailable_distinct`.
6. **Hermetic tests through the shared production path (should-fix 2).** The duplicated test dispatcher is deleted. Every test now drives `run_request`, the same function the Tauri command calls, or the generated handler itself through the `tauri::test` mock runtime. Fixtures use `tempfile::TempDir` and `SecretChoice::SessionOnly`, so no test opens a keychain, a Secret Service bus, an application data directory, or a production or business database. Requests use the canonical nested wire shape `{"contract_version":1,"request_id":…,"command":{"command":…,"args":{…}}}`; the oversized-secret test keeps a valid one-byte credential as the control so it proves the boundary rejects the oversized value only.

## Composition wiring

- `build(root, changes, secrets)` opens `SqliteRepository` against `root/quotavista.sqlite`, a `FileStore` rooted at `root/journal`, the credential store selected by `SecretChoice` (no fallback; a native store that cannot be opened leaves the composition degraded with the typed error of the actual failure), then constructs the `lifecycle::Coordinator` (calls `recover()` so the journal and ledger are reconciled) and the `RefreshCoordinator` (initialised with the first synthetic provider from `synthetic_providers()`). `build_with_provider` takes an explicit provider adapter so a test can inject a failing synthetic scenario. `build_for_tauri` wires the `qv://change` sink and resolves the credential store from `secret_choice_from_env()`.
- `dispatch_command` accepts `Option<serde_json::Value>` (the renderer sends the payload under the key `request`; the Rust parameter carries the same name so the camelCase key matches), decodes it into `Request`, calls `Request::validate(&UtcClock)`, and only then routes to the handler. A decode failure returns `Envelope::Error { contract_version: 1, request_id: "qv-malformed", error: SafeError::new(ErrorCode::Validation, None) }`; the input value is never echoed. `run_request` is that single path, and both the Tauri command and every test use it.
- `list_connections` calls `repository.connections()` and returns a `ConnectionList` whose `data_revision` is the store's commit counter. `refresh_connections` validates the target up front (a sealed `Validation` error for unknown `Selected` ids, never silent filtering), builds a `WriteContext` per connection (its `generation` is the optimistic-revision token the coordinator fences on, so a stale generation is refused instead of overwriting newer state), submits a single `coordinator.request_manual` batch, drives `coordinator.pump()`, and returns one `OperationDto` per admission whose `operation_id` is the coordinator's job id (a refused or cooldown-blocked admission gets a synthetic `admission-<n>` id that stays pollable). When the store revision advanced across the request, the desktop emits a single `ChangeEvent` carrying the new revision and the affected connection and scope ids. `get_operation` reads the coordinator outcome, then the admission records, then the durable lifecycle ledger, and rejects an unknown id with `Validation`; when the poll advances a job that outlived the refresh step budget, the commits that poll produced are announced through `publish_change`. `get_overview`, `query_statistics`, `connect_provider`, `update_connection`, `replace_credentials`, `set_connection_enabled`, `remove_connection`, and `update_settings` return `SafeError::new(ErrorCode::UnsupportedInPhaseOne, None)` - never a generic `InternalError`, never an invented success DTO. `connect_provider` and `replace_credentials` report the degraded credential-store error when the composition runs degraded.

## Review boundaries and open release work

This task wires the desktop composition root and the frontend client; it does not close every release criterion it contributes to.

- `get_overview`, `query_statistics`, `connect_provider`, `update_connection`, `replace_credentials`, `set_connection_enabled`, `remove_connection`, and `update_settings` return `SafeError::new(ErrorCode::UnsupportedInPhaseOne, None)`. The capability file uses the `windows` array to scope the allowlist to the `main` window; additional windows (settings popups, tooltips) would need their own capability file or an explicit `windows: ["main", "<other>"]` allowlist.
- `NativeSecrets` is wired in only on `cfg(macos)` and `cfg(linux)` targets. A native store that cannot be opened leaves the composition degraded with the typed error of the actual failure (`SecretStoreLocked` or `SecretStoreUnavailable`); the session store is never substituted for it. The session store is reachable only through an explicit choice (`SecretChoice::SessionOnly`, or `QUOTAVISTA_SECRET_STORE=session-only` for a production run), which satisfies the requirement that session-only storage needs explicit selection. The macOS native smoke check is intentionally not performed by this worker: the contract is exercised through `SessionSecrets` (a fake in-memory map) and `RefreshCoordinator` over synthetic scenarios, with no keychain, Secret Service bus, application data directory, production, business, or personal database opened, read, or written. A native smoke check is owed by P1-11 and must use only disposable synthetic secrets under a uniquely named `quotavista-test-` service, with cleanup evidence recorded.
- The `qv://change` event channel is wired in the client and emitted from the desktop whenever a commit advanced the store revision: the `refresh_connections` handler after its pump batch and the `get_operation` handler after a poll that advanced a job. The remaining commit-driven emissions (storage/coordinator mutations) land in P1-10 and P1-11.
- `store_state.data_revision` currently advances only in `save_snapshot` and `publish`, so in P1-07 only data commits move it. The P1-10 connection and lifecycle mutations change the connection list without moving that counter, so P1-10 must advance the counter for those writes (or emit its own event) before the renderer can rely on the revision to invalidate the connection list. `list_connections` reads the connection rows and the counter as two separate reads; a data commit does not change the connection rows, so the pair is consistent for P1-07, and P1-10 must re-check that once connection writes exist.
