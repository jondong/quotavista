# Persistence and recovery

Follow [local persistence](../../../docs/architecture.md#local-persistence) and [credential lifecycle](../../../docs/architecture.md#credential-lifecycle-and-crash-recovery).

SQLite is backend-owned, in the OS application-data directory. Use migrations, WAL, a serialized writer, and foreign-key/busy-timeout settings on every connection. Pin a SQLite release with the documented WAL fixes and verify the linked runtime version during setup.

Tokens use canonical integer text with u64 facts and checked u128 totals. Money uses canonical decimal text with explicit currency and checked precision. Never aggregate accounting values through SQLite REAL or JavaScript Number.

Keep snapshots, usage facts, coverage, checkpoints, candidate sync runs, and published partitions distinct. Publish a replacement partition atomically only after completeness is established; a partial candidate must not erase or add to its published predecessor.

Check generation and lifecycle inside the write transaction while holding the per-connection mutation fence. Recovery precedes scheduling. External durable journals contain opaque references only; native secret values never enter SQLite, backups, journals, or fixtures. Deletion must fence late results and purge containing managed backups before acknowledgement.

Phase 1 establishes and fault-tests these boundaries with synthetic data. Full provider synchronization, 90-day retention, and managed restore flows are later-phase work.

## P1-03 adapter contract

`quotavista_core::storage::Repository` is a backend-only async port. `quotavista_infrastructure::sqlite::SqliteRepository::open` requires an explicit path; it is not yet called by the desktop. Until startup recovery and single-instance coordination exist, use it only with throwaway synthetic stores.

- SQLx is pinned to `0.9.0`; `libsqlite3-sys = 0.37.0` bundles SQLite `3.51.3`. Startup and tests assert the linked version (not a system `sqlite3` executable). This version includes the WAL-reset fix; do not enable SQLx's unbundled SQLite feature.
- One writer connection takes `BEGIN IMMEDIATE` before checking generation/lifecycle/scope. Three read-only pooled connections use explicit read transactions for published headers/facts. Each connection sets WAL, foreign keys, a 5-second busy timeout, and FULL synchronous mode. There is no unbounded retry loop.
- All amounts are canonical TEXT. Snapshot token totals support `u128`; fact tokens are bounded to `u64`. Decimal/currency parsing reuses core types. Never use SQLite `SUM(amount)` for accounting.
- `stage_page` compares the previous cursor and commits its page/upserts and next cursor together (1,000 facts/page, 100,000 distinct facts/candidate). `complete_candidate` is an internal caller attestation of complete, settled, untruncated authoritative coverage, not a provider pagination algorithm.
- Publication checks the candidate's base revision and current generation/lifecycle under the writer lock. It deletes/replaces only that partition's facts and commits the pointer, coverage, checkpoint, success time, revision, and staging cleanup together. No incomplete or overlapping source partitions may publish. A repeated published run is a no-op.
- Within one candidate, the last accepted cursor-ordered page wins for a duplicate identity. Stale page retries fail cursor compare-and-swap; opaque `source_revision` strings are retained but not sorted. A provider adapter must resolve conflicting source revisions before attesting the candidate as authoritative; that provider-specific ordering is not implemented here.
- Event identity is scope/dataset/event-id/metric, independent of timestamp and source revision. A correction within a replacement updates one fact. A correction that would move an event across partitions fails closed; multi-partition reconciliation is deferred. Bucket identity includes partition context and half-open bounds.
- Only the initial schema is supported. Reopening validates migration checksums; a pending migration against a populated store is refused until a consistent backup/maintenance coordinator is implemented. Never substitute a copy of a live WAL database. Metadata tables for lifecycle, alerts, and managed backups do not implement those later workflows.

## P1-04 recovery fence contract

`quotavista_core::journal` owns the nonsecret lifecycle model; `quotavista_infrastructure::lifecycle::Coordinator` owns ordering and the per-connection mutation fence; `quotavista_infrastructure::durable::FileStore` owns atomic file replacement. None is composed into desktop startup yet, so use them only with throwaway synthetic stores.

- A journal record is opaque identifiers plus phase: operation id, connection id, kind (`setup`/`replace_credentials`/`delete`), phase (`pending`/`candidate_written`/`committed`/`compensation_pending`/`complete`), optional candidate and previous references, and the captured generation. No credential value, provider identity, alias, scope key, or usage metric may ever enter a record, a ledger entry, or a fixture.
- Encoding is a versioned header plus tab-separated lines. `Journal::decode`/`Ledger::decode` fail closed on a bad header, a wrong field count, an unknown kind/phase/state, a duplicate operation id, or a failing validation; corruption is a visible recovery condition, never "absent means finished". `Journal::record` refuses an operation identifier already held for another connection before the durable replace, so state that could not be decoded again is never written. A `Journal` never holds a `complete` record: `advance(.., Complete)` removes it, so a released fence leaves no external residue.
- `DurableStore::replace` writes a same-directory temporary file, flushes, `sync_all`s, renames over the target, then best-effort syncs the directory. `sync_all` and directory sync are advisory on network shares, removable media, and Windows directory handles; Phase 1 asserts the call sequence and the injected-failure behavior, not media guarantees. A failure returns `Durability` and the caller must stop before writing a secret or acknowledging a deletion. `read` maps a missing file to `Ok(None)` and every other error to `RecoveryRequired`.
- Entry names are restricted to alphanumerics, `-`, `_`, `.` and must not start with `.` or contain `..`, so external state can never address a path outside the store root.
- Ordering is fixed: external intent durable first, then the secret write, then the database projection, then fence release. `Coordinator` mutates external state only through `commit_journal`/`commit_ledger`, which encode a clone and write it durably before adopting it, so a durability failure can never leave memory claiming state the file lacks.
- `&mut Coordinator` *is* the mutation fence: the coordinator is the only writer and holds the borrow through commit. The database re-checks generation, lifecycle, and the incomplete-projection fence inside the `BEGIN IMMEDIATE` transaction (`activate_reference` via `mutation_fence`, result writes via `guard`, lifecycle mutations via `set_lifecycle`) as the final protection, so a caller that ignored the fence still cannot publish a stale result.
- `lifecycle_operations` is the database projection of the journal, not a replacement for it. `guard` refuses a result write while any incomplete operation row exists for the connection; `activate_reference` excludes its own operation id so the activating transaction can commit. A projection may exist without a journal record (an uncommitted restore); recovery reconciles both directions and never trusts the projection alone. `schedule_context` consults projections before admitting a dispatch, because a projection can outlive the journal record whose release dropped the in-memory fence. A candidate reference equal to the connection's live `credential_ref` is refused at admission, so no compensation path can owe a secret still in use.
- `recover()` runs before any mutation or scheduling and is idempotent: it deletes an owed reference, then completes the operation, then acknowledges ledger cleanup. A failure that is `Locked`, `Unavailable`, or `RecoveryRequired` leaves that operation pending and fenced but does not stop recovery for other connections. Scheduling and restore admission require recovery to have run.
- The deletion ledger lives outside the database, records opaque local ids with an optional owning connection id, and is written before the `deletion_pending` transition. It fences scheduling and every managed restore while any entry is `pending_cleanup`, and it keeps fencing ids whose cleanup is complete, because a managed backup may still reintroduce them. Compact an entry only when no managed backup can return that identifier. A `pending_cleanup` entry with no journal record and no projection is an interrupted deletion: recovery resumes it from the ledger alone only once the row is already `deletion_pending`, deleting the reference `connections.credential_ref` names, and `begin_deletion` may be called again rather than being refused by its own fence. Because the ledger is written before the transition, a pending entry alone does not prove the deletion was accepted; a refused or uncommitted compare-and-swap leaves the entry pending so the retry repeats the generation check instead of removing a live credential.
- `admit_restore` validates the manifest, refuses while cleanup is owed, and refuses a manifest whose included opaque ids are ledger-blocked. Restore execution, backup creation, and backup purge are later-phase work.

Run `cargo test --locked -p quotavista-infrastructure` for temporary-file migration/reopen, exact-number, rollback, publication, stale-generation, pool-setting, external-lock, durable-write, and lifecycle recovery fixtures. These tests never resolve or read an application data directory, a native secret store, or a keychain.

## P1-06 simulated provider and refresh contract

`quotavista_core::provider` owns the refresh port (request/response models, typed `ProviderError`, `Cooldowns`, injectable `RefreshClock`); `quotavista_providers::simulated` owns deterministic fixtures; `quotavista_infrastructure::refresh::RefreshCoordinator` owns scheduling, admission, and repository writes. None is composed into desktop startup yet, so use them only with throwaway synthetic stores.

- The providers crate has no network dependency: adapters are constructed from in-memory capability fixtures, every dataset carries `Provenance::Synthetic`, and a `RateLimited` scenario returns a typed error instead of contacting an endpoint. An adapter returns structured data or a `ProviderError`; it never polls, retries, or schedules on its own.
- The coordinator admits at most one job per connection and two running jobs overall; extra admissions queue as pending. A manual request for a connection with a live job coalesces into it. Cancellation is observed between steps and immediately frees the concurrency slot.
- Admission captures the caller's `WriteContext`; every repository write re-checks generation, lifecycle, and scope inside the transaction. A late synthetic response after disable, deletion, or credential rotation fails that check and the job ends `Fenced` — committed values are never overwritten by stale writes. Admission refuses any connection whose lifecycle is not `Active`, so suspended connections never occupy a concurrency slot, and a late provider error for a dead context is fenced without recording health or a cooldown.
- Job ids come from a persisted ordinal (`refresh-counter.v1`, written through `DurableStore` before adoption), so a reopened coordinator never reissues a job id against `sync_runs`. A `Conflict` at candidate start with a connection that still matches the admission context is a run-id collision and is reported as `StorageFailed`, never as `Fenced`.
- Whole-call transport errors (`current()`/`history_page()` failures) record health under the empty dataset key (`(connection, "")`); per-dataset results keep their own keys, so one dataset's failure never clears another's entry.
- A rate-limited response aborts the job and skips history. The cooldown boundary is written to the durable store (`cooldowns.v1`) before it is adopted in memory, so a durability failure never yields a cooldown the next run does not observe. Manual and automatic admissions both respect persisted boundaries, which only move later, never earlier.
- Automatic refresh runs only when `settings.refresh_minutes` is `Some`; with `None` a tick admits nothing and issues no provider query. With `Some(m)` a connection is due only after `m` minutes since its last completion.
- History is bounded per job (100 pages / 30 seconds, measured on the injected UTC `RefreshClock`). Hitting the bound ends the job `Completed { history: Incomplete }`: the partial candidate stays in staging under the run id, the published partition is untouched, and nothing claims completeness. Only the terminal page's `complete` attestation plus a matching cursor CAS may publish — a later truncated page withdraws an earlier attestation. A provider that serves no history at all ends `Completed { history: Skipped }`.

Run `cargo test --locked -p quotavista-infrastructure -p quotavista-providers -p quotavista-core` for fake-clock scheduling, coalescing, cooldown, cancellation, fencing, per-dataset isolation, and partial-history fixtures. These tests never resolve or read an application data directory, a native secret store, or a keychain.
